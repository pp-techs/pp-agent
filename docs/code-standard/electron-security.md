# Electron security rules

Rules enforced in `apps/desktop/src/main/index.ts`, the daemon (`apps/daemon`) and agent-core. Keep them when adding features.

- **Isolated renderer:** `BrowserWindow` uses `contextIsolation: true` and `sandbox: true`. The renderer reaches the system only through the preload bridge (`window.ppAgent`, typed `DesktopBridge`).
- **No navigation:** `will-navigate` is prevented. `setWindowOpenHandler` opens only `http://`/`https://` URLs with `shell.openExternal`; `openExternal` rejects any other protocol.
- **Untrusted IPC input:** `ipcMain.handle` arguments are `unknown`; check types and throw a plain-English error before acting.
- **IPC sender:** register every handler through `TrustedIpc` (`createTrustedIpc` in `apps/desktop/src/main/trusted-ipc.ts`), never `ipcMain` directly: it answers only messages from the main frame of the app window showing the app's own page (the dev server's origin, or the bundled `index.html`).
- **Electron fuses** (`electronFuses` in `apps/desktop/electron-builder.yml`): cookie encryption on, `NODE_OPTIONS` and `--inspect` off, only the integrity-checked `app.asar` loads. `runAsNode` stays on only because the daemon runs as `ELECTRON_RUN_AS_NODE=1 <app> daemon.mjs`; nothing may rely on starting the app binary with `NODE_OPTIONS` or `--inspect`. See [Build and packaging](build-and-packaging.md).
- **Path validation:**
  - Reveal in Finder/Explorer only inside the user-data folder or the workspace (`isInside` in `apps/desktop/src/main/files.ts`). "Open folder" (`openFolder`) opens only a workspace folder from settings, resolved with `realpath`, and on macOS never a bundle (`.app`, `.pkg`, `.workflow`, `.bundle`…), which Finder would run.
  - Session paths from the renderer must resolve inside the session folder and end in `.jsonl` (`requireSessionPath` in `packages/agent-core/src/index.ts`).
  - Workspace folders must be absolute paths to existing (or creatable) folders that no other workspace uses (`packages/agent-core/src/workspaces.ts`).
- **Keys stay in the daemon:** API keys, search keys, MCP sign-ins and the Telegram bot token live in `vault.json` (AES-256-GCM, entry id as authenticated data), whose master key comes from `PP_AGENT_MASTER_KEY`, the OS keyring (`@napi-rs/keyring`), or `vault.key` (mode 0600) as the last resort (`apps/daemon/src/vault/index.ts`). Only the daemon reads the vault; the window never receives a key (`GatewayView` and `TelegramStatus` omit them) and main only decrypts the legacy `credentials.json` once, to import it. `safeStorage` is used for nothing else.
- **Local daemon socket:** the daemon's socket is a Unix socket (mode 0600, in a folder owned by the same user) or a Windows named pipe. Every client must answer the daemon's `challenge` within 5 s with a `hello` carrying a fresh nonce and an HMAC proof keyed by the token in `agentd.token` (mode 0600); the token itself is never sent, and proofs are compared in constant time. A new transport or a network listener needs its own authentication and a decision recorded in [Key decisions](../project-pdr/key-decisions.md).
- **Phone access (the one network listener):** off by default and switched on only from the computer. It binds every interface but answers only local-network source addresses (`isLocalNetworkAddress`: private IPv4, link-local, IPv6 unique-local and link-local, carrier-grade NAT only while the computer itself has such an address; loopback only with a loopback `Host`), and only a `Host` that names the computer (`isOwnHost`, 421 otherwise, against DNS rebinding). Devices pair with a one-time code (wrong codes locked per source address and globally) and then send a per-device token in `Authorization` (never a cookie or a URL); only its hash is stored, and a token unused for 30 days stops working. Devices are refused the commands in `remoteMayRun` (`packages/shared`): anything that lets the computer run programs without an approval (MCP servers, tool policies, turning on the shell or yolo mode, always allowing or unblocking an app, including `respond_approval` with `remember: "always"`), Telegram and Zalo set-up, creating a workspace, bulk deletions, the login service, and phone access itself. Attachments from a device must be its own uploads. Keep new commands in mind: one that adds a way to run programs unattended, gives someone else a way in, or deletes in bulk belongs in `REMOTE_LOCAL_ONLY_COMMANDS`. See [Phone access](../architecture/phone-access.md).
- **Channels trust one person:** the Telegram bot answers only the paired owner's private chat, ignores everyone else, and accepts a pairing code only while the person has opened a pairing window in Settings (`packages/agent-core/src/channels/telegram/`). New channels must keep an owner check before anything reaches `AgentHost.gateway`, and approvals must be answerable only by that owner.
- **Approval gate:** tools that write or execute ask before running according to their tool tier and tool policy (`packages/agent-core/src/tools.ts`). New tools must declare a tier; untiered tools ask.
- **Model-controlled URLs:** `web_fetch` connects only through `guardedLookup` (`packages/agent-core/src/web/fetch.ts`), which refuses private, loopback, link-local and metadata addresses at connect time and on each redirect. Any new tool that fetches a model-supplied URL must reuse it. The agent's browser tool cannot use a lookup hook, so `BrowserHost` cancels every main-frame and subframe load of the agent's pages whose host resolves into the same ranges (`isPrivateTarget` in `apps/desktop/src/main/browser/address.ts`); pages the person drives are not limited. Search-provider requests use fixed or user-configured URLs and are not model-controlled.
- **No remote images in replies:** the renderer's CSP allows images only from `'self' data: blob:` (`apps/web/vite.config.ts`), and chat Markdown passes Streamdown a `harden` setup with no allowed image prefixes (`apps/web/src/components/markdown.tsx`), so a blocked image shows only its description. An image would load the moment a reply shows it, letting a prompt-injected model send what it read to any server without a tool call. Keep both when rendering model text.
- **Updates:** only builds the release workflow signed (`ppCodeSigned` in their `package.json`) install updates in-app; others open the release page (`apps/desktop/src/main/updates.ts`).

## Side panel

- Terminals and file listings accept only a workspace folder from `settings.json` (or the default one); file paths are resolved with `realpath` and must stay inside it, so a symbolic link cannot lead out.
- Browser pages are `WebContentsView`s with `sandbox`, `contextIsolation`, no Node and no preload, in their own partition per profile. They navigate only to `http(s):`/`about:blank`, and each partition's permission handlers allow only fullscreen, pointer lock and clipboard writes. See [Side panel](../architecture/side-panel.md).
- Imported cookies are read from temporary copies of the browser's databases, in a utility process, and never logged. Only the sites the person picks are imported, never the whole jar. The macOS Keychain item is read in-process (`@napi-rs/keyring`), so the prompt and "Always Allow" name PP Agent rather than `/usr/bin/security`; Windows tools run by full path (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`), never through PATH; app-bound cookies are read over `--remote-debugging-pipe`, never a debugging port another program could connect to.
